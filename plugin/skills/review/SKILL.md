# Review round

The review itself runs in the `qrispy:reviewer` agent, a subagent that cannot see this conversation. This session prepares, guards and records it. Never write the review yourself, and never edit the reviewer's text.

1. **Pick the round.** `N` = highest existing `revN.md` in the ticket directory plus one. Tell the user the local time you start (delegation timestamp).
2. **Guard snapshot.** Hash what the reviewer must not change:

   `qrispy review freeze <ticket> <N>` writes the sha256 of every file in the ticket directory except `rev<N>.md`, of the shared `<ticket root>/*.md` documents, of the plugin's `method/*.md` files and of the ticket's deliverable (when `state.json.deliverable` is one existing file) to `guard_before.txt` in `S=<review scratch>/<ticket>/rev<N>` (`qrispy config review-scratch` prints the review scratch folder). Below, `T` is the ticket directory (`qrispy config ticket-dir <ticket>`).

3. **Run the reviewer.** Default route (the reviewer must not show up as another session): the `qrispy:reviewer` subagent (`${CLAUDE_PLUGIN_ROOT}/agents/reviewer.md`, Opus, effort high, no Edit/Write). Run `qrispy review freeze <ticket> <N>` (does step 2), then call the Agent tool with `subagent_type: qrispy:reviewer` and the prompt exactly `TICKET=<ticket> ROUND=<N>` and nothing else, so the worker cannot steer the review. A ticket of the primary system (the first in `qrispy.json`) is named by its slug, a ticket of another system by its path `<root>/NNN-slug`. When it returns, run `qrispy review record <ticket> <N> <output_file>` with the `output_file` path the Agent tool printed (the subagent transcript; `record` takes the report from its `SubagentHandback` call, because the copy shown in the chat is indented by the harness). `record` does steps 4 and 5. If a safeguard refuses or the agent stops early, do not repeat the call: report it, check the hashes, and use the headless route below.

   Fallback route: a separate headless session on Opus: `qrispy review start <ticket> <N>` does steps 2 and 3 for you (freezes the hashes, writes the prompt and run script, launches the reviewer as a tracked job; `--dry-run` shows what it would do). Then start `qrispy job wait` on the job directory it prints as a background command, and check on it every few minutes with `qrispy job status` as the long-running-work section of the `qrispy:ticket` skill says. Do not edit the ticket directory or `<ticket root>/*.md` while it runs. The headless route auto-allows `python3`, which the git hook cannot see into, so its guarantee is the contract in `${CLAUDE_PLUGIN_ROOT}/method/REVIEW_PROMPT.md` plus the after-the-fact checks (hashes, and a working-tree status warning in `finish`).
4. **Guard check** (`qrispy review finish <ticket> <N>` runs steps 4 and 5 together, plus the husk and attestation checks). Recompute the hashes into `guard_after.txt` and diff. A difference inside the ticket directory discards the round: save the text to `$S/rev<N>.discarded.md`, tell the user what changed, and stop. A difference only in shared `<ticket root>/*.md` files or the plugin's `method/*.md` files is usually another session; report it and check modification times before trusting the round.
5. **Record verbatim.** Write the returned text unchanged to `$T/rev<N>.md`. It must start with the `QRISPY-REVIEW-PROTOCOL` block followed by the `QRISPY-REVIEW-META` block; if it does not, or it is under ~4 kB of substance, treat it as a failed round (a husk) and rerun, never pad it.
6. **Register.** Append `{"review": "rev<N>.md", "response": null, "verdict": …, "blocking_open": …, "date": …}` to `state.json.reviews`, add each blocking finding's one-line summary to `awaiting_user` only if it needs a user decision, and report elapsed time since step 1.
7. **Respond.** Re-read `${CLAUDE_PLUGIN_ROOT}/method/DEV_REVIEW_RECIPE.md` §B (review rounds) first; before declaring any artifact canonical, run its §A1 checklist. Write `rev<N>_response.md` from `${CLAUDE_PLUGIN_ROOT}/skills/ticket/templates/rev_response.md`: one section per finding ID of `rev<N>.md`, each with the quoted claim, the verdict, every location found by a written-out search, the change at each location, the re-check on disk, and for an accepted code finding the regression test (`DEV_REVIEW_RECIPE.md` §B3a; corrections still clustered by resource gate). Register it in `state.json.reviews` (`"response": "rev<N>_response.md"` in the `rev<N>.md` entry; `qrispy lint` warns when it is missing). Run `qrispy check-response <rev<N>.md> <rev<N>_response.md>` (also part of `qrispy lint`) before telling the user the response is done; write "fixed" only after the location list was searched and each location re-read. Each finding carries a mistake class; findings that are your own mistakes go to `<ticket root>/LESSONS.md` in the same turn.

A verdict of `MAY_CLOSE` is the reviewer's opinion, not permission to close: closing remains the user's call.
